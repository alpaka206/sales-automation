# 데이터 스냅샷을 로컬에서 보는 길 — 설계 (2026-09-10)

대상: `perso-data-snapshot` (GitHub 비공개 저장소 `est-perso/perso-data-snapshot`)

목표(운영자):
1. 그 데이터가 **우리 서버·DB 에 절대 안 올라간다**
2. 하루 한 번 `pull` 을 자동으로 받는다
3. 로컬에서 띄워서 본다
4. 우리 사이트에서 **실행 파일을 받아** 그 폴더 옆에 두고 실행하면 ①②③ 이 된다
5. 되면 좋은 것: 사이트에서 그 실행 파일까지 띄운다

---

## 0. 먼저 — 스냅샷이 무엇인지 (실제로 열어 봤다)

| | |
|---|---|
| 정체 | **git 저장소 clone**. `.git` 팩 532MB + 작업본 CSV 48개(약 470MB) = zip 591MB |
| 내용 | 운영 MySQL 을 테이블별 CSV 로 내린 것 — user·space·subscriber·project·payment·credit… |
| 만드는 쪽 | Azure Functions Timer 가 **매일 05:00 KST** 에 변경분만 단일 커밋으로 push |
| PII | 이메일·이름·연락처·billing key 등은 **SELECT 단계에서 제외**(마스킹 아님). 다만 제목·파일명 같은 유저 입력 텍스트는 들어 있어 **사내 전용** |
| 이미 있는 것 | `data/README.md`(LLM 용 데이터 사전) · `data/manifest.json`(테이블·컬럼·기간·FK) |
| 저장소가 권하는 분석 도구 | **DuckDB** (`read_csv_auto`) — README 예시가 그렇게 쓴다 |
| 저장소에 남아 있는 옛 뷰어 | Next.js + FINOS Perspective (`npm run dev` → :3010). **MySQL 에 직접 붙는 것**이라 CSV 분석에는 못 쓴다 |

**즉 「우리 서버에 안 올린다」는 이미 지켜져 있다** — 그 데이터는 처음부터 다른 저장소에 있고,
우리 앱은 그것을 모른다. 지켜야 할 것은 **앞으로도 우리 쪽으로 흘리지 않는 것**이다.

## 1. 웹에서 로컬을 읽을 수 있나 — 확인한 사실

운영자가 「웹에서 로컬 파일 읽어오는 거 안 되는 걸로 안다」고 했다. **반은 맞다.**
정확히는 세 갈래가 있고 각각 다른 벽이 있다.

### 1-1. 브라우저가 로컬 **파일**을 직접 읽기 — `showDirectoryPicker()`

| 브라우저 | 가능? |
|---|---|
| Chrome 86+ · Edge 86+ · Opera | ✅ |
| **Safari** | ❌ (OPFS 만, 로컬 디스크 피커 없음) |
| **Firefox** | ❌ |

→ **Chromium 전용.** 그리고 사용자가 매번 폴더를 고르는 제스처가 필요하다.

### 1-2. 웹 페이지가 로컬 **서버**에 붙기 — `https://우리사이트` → `http://127.0.0.1:PORT`

여기가 핵심이고, **최근에 바뀌었다.**

| 브라우저 | 현재 동작 |
|---|---|
| Chrome / Edge | **Chrome 141(2025-09-30)에 예고, 142 에서 시행** — 공개 출처가 로컬·루프백에 접근하면 **Local Network Access 권한 프롬프트**가 뜬다. 허용하면 된다. 요청 쪽은 **HTTPS(보안 컨텍스트) 필수**이고, 개발자는 요청에 `targetAddressSpace: "local"` 을 붙인다 |
| Firefox | 루프백은 mixed content 예외라 동작 |
| **Safari** | ❌ **차단.** 「mixed-content `http://localhost` 요청을 막는 유일한 브라우저」이고 **프롬프트도 안 뜬다** |

→ **우리 사이트에서 로컬에 붙는 길은 Chrome/Edge 에서만 되고, 거기서도 사용자가 권한을
한 번 눌러야 한다. Safari 에서는 아예 안 된다.**

### 1-3. 로컬 서버가 **자기 UI 를 자기가** 띄우기 — `http://127.0.0.1:PORT` 를 직접 연다

이 경우 페이지 출처 자체가 루프백이다 → **mixed content 없음, LNA 프롬프트 없음**
(같은 주소 공간끼리는 프롬프트가 안 뜬다), CORS 없음.

→ **모든 브라우저에서 되고, Safari 도 된다.** 제약이 하나도 없다.

### 1-4. 사이트에서 실행 파일을 띄우기

가능한 방법은 **커스텀 URL 스킴** 하나뿐이다(`persodata://…`). 설치된 앱이
Windows 레지스트리 / macOS `Info.plist` 에 스킴을 등록해 두면, 웹 페이지의 링크가 그 앱을 깨운다.
Zoom·Slack·Figma 가 쓰는 그 방식이다.

한계 둘:
- **설치 여부를 안정적으로 알 수 없다.** 브라우저마다 감지 방법이 다르고 전부 우회 기법이다
  (Chrome 은 `window.onblur` 로 포커스가 뺏겼는지 보는 식).
- 스킴 인자는 **악의적 입력으로 간주**하고 검증해야 한다(따옴표·백슬래시로 인자 주입).

→ **「사이트에서 실행」은 되지만, 앱이 먼저 설치돼 있어야 한다.** 첫 실행은 어차피 사람이 한다.

## 1-5. 운영자 답을 반영하면 — **부딪치는 요구가 하나 있다**

| 답 | 뜻 |
|---|---|
| 「브라우저는 다 풀어놓는 게 좋지 않을까」 | **Safari 를 포함한다** |
| 「저 데이터에 대한 정보가 아예 안 나갔으면」 | 원본도, 계산 결과도 이 PC 밖으로 안 나간다 |
| 「연산은 로컬에서, 계산된 값이 연동되게」 | 집계는 로컬에서 만들고, 그 값을 화면에서 본다 |
| 「여러 명이 쓴다」 | 한 사람용 편법(내 PC 에만 되는 설정)은 못 쓴다 |
| 「읽기만 하면 된다」 | 되돌려 쓰는 경로가 없다 — `pull --ff-only` 로 충분하고 충돌이 없다 |

**부딪치는 자리**: 「여러 명」 + 「아무것도 안 나간다」 = **팀이 같은 숫자를 보는 화면은
존재할 수 없다.** 각자 자기 PC 에서 자기 clone 을 계산하고 자기 화면을 본다.
숫자 하나를 팀이 같이 보려면 그 숫자는 **적어도 한 번은 어느 PC 밖으로 나가야** 한다.

이건 기술 문제가 아니라 **정의상 그렇다.** 어느 쪽을 고를지가 이 설계의 유일한 갈림길이다.

### 네 가지 모양

| | 원본 | 집계 | 우리 콘솔에서 보나 | 브라우저 | 팀이 같은 숫자를 보나 |
|---|---|---|---|---|---|
| **A. 각자 로컬에서 본다** | 안 나감 | 안 나감 | ❌ 링크만 | 전부 | ❌ |
| **B. 콘솔이 로컬에서 가져와 그린다** | 안 나감 | 안 나감<br>(브라우저↔로컬만, 서버 저장 없음) | ✅ | ❌ **Chrome/Edge 만** | ❌ |
| **C. 집계만 서버로 올린다** | 안 나감 | **나감** | ✅ | 전부 | ✅ |
| **D. 로컬이 콘솔 모양의 화면을 띄운다** | 안 나감 | 안 나감 | △ 「우리 콘솔처럼 보이는 로컬 화면」 | 전부 | ❌ |

**B 는 Safari 에서 안 된다** — 그게 1-2 의 결론이다. 「다 풀어놓자」와 B 는 같이 못 간다.

**D 를 권한다.** 런처가 우리 콘솔과 같은 CSS·컴포넌트로 화면을 만들어 `127.0.0.1` 에서
띄운다. 페이지 출처가 루프백이라 **모든 브라우저에서 되고**(Safari 포함), 원본도 집계도
그 PC 를 안 떠난다. 「우리 사이트와 연결」은 **콘솔에 「데이터 분석 열기」 버튼**과
로컬 화면의 「콘솔로 돌아가기」 링크로 만든다.

### ⚠️ D 에서 한 가지 — 우리 콘솔 데이터를 같은 화면에 못 얹는다

로컬 화면(`http://127.0.0.1:PORT`)에서 우리 API(`https://…onrender.com/api/ui/…`)를 부르는 것
자체는 **막히지 않는다** — HTTP 페이지가 HTTPS 를 부르는 것은 mixed content 가 아니고,
루프백은 보안 컨텍스트라 제약도 없다. 막는 것은 **우리 쪽 두 가지**다.

1. 세션 쿠키가 `SameSite=Lax` (`api/auth.py`) → **다른 사이트에서 부르면 안 실려 간다**
2. 미들웨어의 `is_same_origin_browser_request` 가 **cross-site 요청을 403 으로 막는다**
   (`api/main.py:273`)

둘 다 일부러 그렇게 해 둔 CSRF 방어다. 풀려면 쿠키를 `SameSite=None` 으로 바꾸고 CORS 허용
출처를 여는 것인데, 그건 **콘솔 전체의 CSRF 방어를 로컬 도구 하나 때문에 낮추는 것**이라
권하지 않는다.

→ **로컬 화면은 스냅샷 데이터만 다룬다.** 우리 콘솔 데이터와 나란히 놓고 싶으면 그때
「집계만 서버로」(C)를 검토한다 — 그 순간 「아무것도 안 나간다」를 포기하는 것이므로
따로 결정할 일이다.

## 2. 그래서 어떤 모양이 맞나

**1-3 이 답이다.** 사이트가 로컬에 붙는 게 아니라, **런처가 자기 UI 를 로컬에서 연다.**
그러면 Safari·Firefox·Chrome 어디서도 되고 권한 프롬프트도 없다.

우리 사이트의 역할은 셋으로 줄어든다.

```
  우리 콘솔 (https://…onrender.com)
   ├─ ① 런처 내려받기 (Windows / macOS)
   ├─ ② 쓰는 법 한 장
   └─ ③ [데이터 열기] ─ persodata://open ─▶ 이미 설치돼 있으면 런처를 깨운다
                                             (없으면 아무 일도 안 남 → ① 로 안내)

  로컬 (사용자 PC)
   perso-data-snapshot/        ← 지금 그 폴더
   perso-data.exe / .app       ← 그 옆에 둔다
        │
        ├─ 1. 폴더 확인 (자기 옆 `perso-data-snapshot/`)
        ├─ 2. git pull  (하루 한 번, 마지막 pull 시각을 파일에 적어 둠)
        ├─ 3. DuckDB 준비 (없으면 공식 단일 바이너리 내려받음)
        ├─ 4. 127.0.0.1:<포트> 에 서버 시작
        └─ 5. 기본 브라우저로 그 주소를 연다
```

### 2-1. 「사이트에서 붙어서 본다」를 굳이 하려면

Chrome/Edge 한정으로는 가능하다. 우리 콘솔 화면에 지표를 그리고 싶을 때 쓴다.

- 런처가 `Access-Control-Allow-Origin: https://<우리 도메인>` 만 허용(와일드카드 금지)
- 콘솔은 `fetch(url, { targetAddressSpace: "local" })`
- 사용자는 **LNA 권한을 한 번 허용**
- Safari 사용자에게는 이 화면이 안 뜬다 → 「런처에서 보세요」로 떨어져야 한다

**권고: 1단계에서는 만들지 않는다.** 2-1 은 「우리 콘솔에 그 데이터를 지표로 얹고 싶다」가
확정된 뒤에 붙인다. 지금 목적(인사이트 탐색)은 1-3 으로 충분하고, 브라우저 분기가 안 생긴다.

## 3. DuckDB 가 이미 절반을 해 준다

찾아보니 만들 것이 생각보다 적다.

- DuckDB CLI 는 **의존성 없는 단일 바이너리**다 (Windows·macOS·Linux 각각 배포).
- **`duckdb -ui`** 가 `ui` 확장을 자동 설치하고 **로컬 HTTP 서버(기본 `localhost:4213`)를 띄운 뒤
  기본 브라우저를 연다.** SQL 노트북 UI 가 그 안에 들어 있다.
- CSV 는 `read_csv_auto('data/*.csv')` 로 바로 읽는다. 1GB 는 DuckDB 에게 작은 축이다.

→ **런처가 분석 UI 를 새로 만들 필요가 없다.** 런처는 「pull → duckdb -ui 실행」이면 되고,
거기에 우리가 더할 것은 **미리 만든 뷰/질의**(자주 보는 지표를 `.sql` 로) 정도다.

| | 만들 것 |
|---|---|
| 분석 UI | ❌ DuckDB UI 를 쓴다 |
| 쿼리 엔진 | ❌ DuckDB |
| 런처 | ✅ 작다 — 폴더 확인 · pull · duckdb 준비 · 실행 · 브라우저 열기 |
| 초기 뷰 | ✅ `views.sql` — 자주 쓰는 조인·지표를 뷰로 (`manifest.json` 의 FK 활용) |

## 4. 런처를 무엇으로 만드나

| 후보 | 장점 | 문제 |
|---|---|---|
| **Go (CGO 없음)** | 단일 정적 바이너리. **한 대에서 Windows·macOS(arm64/amd64) 전부 크로스 컴파일** | DuckDB 를 임베드하려면 CGO 가 필요 → **임베드하지 않고 CLI 를 호출**하면 해결 |
| Python + PyInstaller | 저장소가 이미 파이썬 | **각 OS 에서 빌드해야 한다** (Mac 바이너리는 Mac 에서). 용량 큼 |
| Node + pkg/SEA | 스냅샷 저장소가 Node | 런타임 동봉으로 무겁고, 역시 OS 별 빌드 |
| 스크립트 (.bat / .command) | 만들기 제일 쉬움 | 더블클릭 UX 나쁨, macOS 에서 권한·격리 경고, 서명 불가 |

→ **Go + DuckDB CLI 호출**을 권한다. 런처 자체는 수백 줄이고, 크로스 컴파일이 한 줄이다.

### 4-1. ⚠️ 서명 — 여기가 제일 아프다

- **macOS**: 서명·공증(notarize)이 안 된 바이너리는 Gatekeeper 가 막는다. 그리고 **Sequoia
  부터 우클릭→열기 우회가 없어졌다** — 사용자가 ① 실행 시도 ② 경고 닫기 ③ 시스템 설정 →
  개인정보 보호 및 보안 → 맨 아래 「그래도 열기」 ④ 관리자 암호. **매 새 버전마다** 반복.
  없애려면 Apple Developer Program(연 $99) + 공증이 필요하다.
- **Windows**: 코드 서명 인증서가 없으면 SmartScreen 이 「알 수 없는 게시자」 경고를 띄운다.
  「추가 정보 → 실행」으로 지나갈 수 있다(막히지는 않는다).

**이건 코드로 못 푼다. 조직 차원의 결정이다.**

## 5. 하루 한 번 pull — 확인해야 할 것

### 5-1. 인증 (미결)

`origin` 이 `https://github.com/est-perso/perso-data-snapshot.git` 인 **비공개** 저장소다.
`git pull` 이 자동으로 되려면 자격 증명이 이미 저장돼 있어야 한다.

| 경로 | 되나 |
|---|---|
| 지금 그 폴더를 clone 한 그 PC | Git Credential Manager(Windows)·osxkeychain(macOS)에 토큰이 남아 있으면 **그냥 된다** |
| 다른 PC / 다른 사람 | ❌ 각자 한 번은 인증해야 한다 |

→ 런처는 **git 을 직접 부르고**(`git -C <폴더> pull --ff-only`), 실패하면 **왜 실패했는지 그대로
보여 준다.** 자격 증명을 우리가 들고 있지 않는다 — 토큰을 런처에 넣으면 그 토큰이 배포된다.

### 5-2. 저장소가 커진다

지금도 팩이 532MB 인데 **매일 1GB 어치 CSV 를 커밋**한다. 몇 달이면 clone 이 수 GB가 된다.

- 새로 받는 사람: `git clone --filter=blob:none --depth 1` (부분·얕은 clone)
- 이미 있는 폴더: `git pull --ff-only` 로 충분하지만, 커지면 `git gc` 나 재-clone 이 필요해진다
- 런처가 **pull 에 걸린 시간과 폴더 크기를 화면에 적어** 두면 언제 손볼지 보인다

### 5-3. 하루 한 번을 누가 재나

런처가 **실행될 때** 마지막 pull 시각을 보고 24시간이 지났으면 받는다. 상주 데몬을 만들지
않는다 — 상주는 자동 시작·업데이트·꺼짐 처리가 전부 따라온다.

## 6. 안전 — 이건 양보하지 않는다

1. **`127.0.0.1` 에만 바인딩한다.** `0.0.0.0` 이면 같은 와이파이의 누구나 사내 데이터를 본다.
2. **CORS 는 우리 도메인 하나만** (2-1 을 만들 때). `*` 는 아무 사이트나 로컬 데이터를 읽는다.
3. **런처는 데이터를 어디로도 보내지 않는다.** 텔레메트리·에러 리포트 포함.
4. **우리 콘솔은 이 데이터를 저장하지 않는다.** 2-1 을 만들더라도 화면에 그릴 뿐 DB 에 안 쓴다.
5. 스킴 인자(`persodata://…`)는 검증한다 — 폴더 경로를 받지 않고, 「열어라」만 받는다.

## 7. 단계

| 순 | 무엇 | 크기 |
|---|---|---|
| 0 | **DuckDB 로 이 스냅샷을 직접 열어 본다** — 지표가 실제로 나오는지 확인 | 반나절 |
| 1 | `views.sql` — 자주 볼 조인·지표를 뷰로 | 보는 것이 정해진 뒤 |
| 2 | 런처(Go) — 폴더 확인 · pull · duckdb 준비 · 실행 · 브라우저 | 1~2일 |
| 3 | 우리 콘솔에 내려받기 화면 + 쓰는 법 | 반나절 |
| 4 | `persodata://` 스킴 등록 + 콘솔의 「데이터 열기」 버튼 | 반나절 |
| 5 | *(선택)* 콘솔이 로컬에 붙어 지표를 그린다 — **Chrome/Edge 전용** | 별건 |

**0 을 먼저 한다.** 런처는 「매번 pull 하고 duckdb 켜는 것이 귀찮다」가 확인된 뒤에 만들 물건이지,
그전에 만들면 아무도 안 쓰는 실행 파일이 하나 생긴다.

## 8. 운영자에게 물어볼 것

| # | 질문 | 왜 필요한가 |
|---|---|---|
| ① | **브라우저를 Chrome/Edge 로 고정할 수 있나?** Safari 를 써야 하나? | 2-1(콘솔이 로컬에 붙기)의 가부가 여기서 갈린다. Safari 면 그 길은 아예 없다 |
| ② | **쓸 사람이 본인 한 명인가, 팀인가?** | 한 명이면 서명·배포가 거의 필요 없다(스크립트로 충분). 여럿이면 4-1 의 서명 문제가 실제 비용이 된다 |
| ③ | **Apple Developer Program 계정이 있나?** (연 $99) | 없으면 macOS 사용자는 새 버전마다 「그래도 열기」 + 관리자 암호를 반복한다 |
| ④ | **지금 그 폴더를 어떻게 clone 했나?** (GitHub Desktop / `gh` / PAT / SSH) | 자동 pull 이 그대로 되는지가 여기서 정해진다. 안 되면 첫 실행에 인증 한 번이 필요하다 |
| ⑤ | **보고 싶은 것이 「SQL 로 직접 파는 것」인가, 「정해진 지표를 보는 것」인가?** | 전자면 DuckDB UI 로 끝이고 런처만 만들면 된다. 후자면 `views.sql` 과 화면이 따로 필요하다 |
| ⑥ | **런처를 어디서 내려받게 하나?** 우리 콘솔인가, GitHub Releases 인가 | 콘솔은 무료 인스턴스(512Mi)라 수십 MB 바이너리를 얹으면 배포 zip 과 메모리에 그대로 얹힌다. GitHub Releases 가 맞아 보인다 |
| ⑦ | **이 스냅샷을 우리 콘솔 화면에 지표로 얹을 생각인가?** | 아니면 5단계를 아예 안 만든다. 「인사이트 활용」이 어디에 쓰이는지가 이걸 정한다 |
