# 사용 데이터(스냅샷)

원칙은 `CLAUDE.md` 의 「사용 데이터(스냅샷)는 서버로 안 간다」 첫 문단에 있다. 여기는 그 세부 규칙이다.

- **2026-10-01 에 PC 마다 깔던 로컬 에이전트를 걷어내고 이 길로 바꿨다** (운영자: 「1로 해야하고 서버엔 절대
  노출금지」). 그전에는 각자 PC 에 스냅샷을 clone 하고 `agent/` 의 에이전트가 그 PC 에서 집계해 `127.0.0.1:43110`
  에 띄웠다. 원칙은 지켰지만 **설치 · 업데이트 · 스냅샷 받기가 PC 마다 따로 깨졌다** — 맥은 공증한 `.app` 이어야
  열렸고, pull 은 며칠 밀리거나 엑셀로 저장한 CSV 하나에 멈췄고, 1.4.x 는 스스로 못 올라가 손으로 받아야 했다.
  그리고 PC 마다 자기 clone 으로 계산하니 **팀이 같은 숫자를 본다는 보장이 없었다.** 지금은 하루 한 번 한 벌을
  가공하고 모두 그것을 본다. 옛 설계 기록은 `docs/데이터-에이전트-설계.md` · `docs/데이터-스냅샷-로컬-분석-설계.md`
  · `docs/로컬-웹-연결-조사요청.md` 이고, 맨 위에 걷어냈다고 적었다.
  - **첫 실가공은 2026-10-06** (운영자가 가공 레포에 워크플로를 넣고 손으로 돌렸다): 그날 09:00 스냅샷을 09:49 에
    가공 · 스페이스 2,153 · 묶음 140 · 파일 146, `data` 는 봇이 만든 부모 없는 커밋 하나. 운영 콘솔의 「데이터 분석」 ·
    수주 고객 목록 · 상세 세 탭(크레딧 · 작업 성능 · 영상 분석)이 그 파일로 그려지는 것을 확인했다.
  - **같은 날 에이전트 시절 코드의 나머지도 걷었다** (운영자: 「이전의 에이전트 코드는 모두 정리해도 되겠다」):
    실행 파일에 DuckDB zip 을 싣던 `duckdb_windows/darwin/other.go` · 캐시에 풀던 `ensureDuckDB` · `agent/bin`,
    모듈 이름 `perso-agent`(→ `perso-export`), 화면 파일 `DataAgent.tsx`(→ `DataStatus.tsx`). DuckDB 는 이제
    `--duckdb` 나 `PATH` 에서만 찾고, CI 의 `exporter` 잡이 같은 버전 · 체크섬을 받아 가공 범위 SQL 테스트가 실제로
    도는지까지 본다. **폴더 이름 `agent/` 만 남긴다** — 가공 레포의 `export.yml` 이 그 경로로 받아 빌드한다.
- **가공 레포의 이름과 그 회사 계정은 이 저장소 어디에도 적지 않는다** — 이 저장소는 공개다. 워크플로 견본
  (`agent/export/perso-usage-data.yml`, 운영자가 가공 레포의 `.github/workflows/export.yml` 로 복사한다)도 자기
  레포를 `${{ github.repository }}` 로만 가리킨다. 토큰은 Render 대시보드와 가공 레포의 Actions 시크릿에만 산다.
- **가공은 09:15 KST(`cron: "15 0 * * *"`) 한 번과 손 실행이다** (운영자: 「github action은 아침 9시 15분에만 돌면 돼
  그때 한번만 받아오면 돼」). 스냅샷이 00:00 UTC(09:00 KST)에 서고, GitHub 의 예약 실행은 몇 분~수십 분 늦을 수 있다.
  그날 스냅샷이 아직 안 올라오기 시작했으면 어제 것을 한 번 더 가공한다. **올라가는 중이면 5분마다 다시 받아 최대
  45분 기다리고, 그래도 안 끝났으면 가공하지 않는다** — 스냅샷은 큰 표를 하나씩 커밋하고 `manifest.json` 을 맨 마지막에
  실어서(스냅샷 저장소 HANDOFF.md 「증분 커밋 전환」: 「manifest가 항상 마지막」), 그대로 가공하면 오늘 표와 어제 표가
  섞인 숫자가 어제 시각을 달고 선다(워크플로의 「스냅샷이 다 올라왔나」: `data/` 를 건드린 마지막 커밋이 manifest 의
  커밋이어야 한다). 기다리는 이유: 09:00 은 만들기를 **시작**하는 시각이라 올리기가 15분을 넘는 날 하루 한 번의 예약이
  빈손으로 끝난다. 다시 받을 때 토큰은 그 git 명령에만 주고 `.git` 에 남기지 않는다(테스트가 고정). 가공이 실패해도
  `data` 는 어제 것 그대로라 화면은 안 비고, 스냅샷이 **36시간** 넘게 묵으면 「· 낡음」을 단다.
  - **가공기는 커널이 가둔다** — `unshare --net --mount --pid` 안에서 `/run` 을 빈 tmpfs 로 덮고(systemd-resolved ·
    D-Bus · docker 소켓 — 바깥 네트워크를 쥔 로컬 데몬이라 네트워크 이름공간만으로는 DNS 조회에 실어 보내는 길이
    남는다) `setpriv` 로 `nobody` · 보조 그룹 없음 · `no_new_privs` 로 내려와 돈다. 스냅샷과 가공기는 읽기 전용으로,
    쓸 곳은 `result/` 하나다. 커널이 지키는 것은 「밖으로 못 보낸다 · sudo 로 root 가 못 된다 · 다음 단계가 실행하는
    러너의 파일을 못 고친다 · 끝나면 다 죽는다」까지다 — **`result/` 의 JSON 에 무엇을 싣는지는 커널이 아니라 아래의
    「고른 커밋」(사람의 검토)과 계약 검사가 지킨다.** 코드에도 네트워크가 없다 — HTTP 도, 바깥에 닿는 git 도(스냅샷은
    워크플로의 「스냅샷 받기」가 받아 준다). 가공 코드 체크아웃은 `persist-credentials: false`.
  - **스냅샷 저장소에는 받기만 한다 — 회사 계정이 쓰기 권한을 가져도 같다** (2026-10-02 운영자: 「쓰기 권한이 있더라도
    스냅샷 저장소에는 아무 문제 없도록 해줘」 — 지금 권한은 읽기다). classic `repo` 토큰은 계정이 쓸 수 있는 곳이면
    쓰기까지 열어서, 「안 쓴다」를 토큰의 권한이 아니라 그 토큰을 쥔 「스냅샷 받기」 **한 단계**가 지킨다: 토큰은 그
    단계에만 있고 어떤 액션에도 안 넘긴다(`actions/checkout` 대신 러너의 git) · 그 git 은 `env -i` · 전역/시스템 설정
    없이 `/usr/bin/git` 으로 돌아 앞 단계가 남긴 insteadOf · 프록시 · 인증서 · `GIT_*` 가 토큰을 딴 데로 못 보낸다 ·
    토큰은 명령줄 `-c` 로만 가고 변수는 머리글을 만든 뒤 지운다 · 그 클론의 push 는 없는 주소로 막혀 있다(`pushurl` ·
    `pushInsteadOf` — 로컬 실측으로 원격 · https · http push 가 전부 그 자리에서 실패) · git 명령은 init · remote add ·
    config(push 막기) · fetch · log · checkout 뿐이고 원격은 스냅샷 저장소 하나 · 미는 단계의 열쇠는 `github.token`
    이라 가공 레포 밖을 못 건드린다. 액션 둘(`actions/checkout` · `actions/setup-go`)은 **40자 커밋 번호로** 고정한다 —
    태그는 옮겨질 수 있고 그 둘은 토큰을 쥔 단계보다 먼저 돈다. 방아쇠는 예약과 손 실행뿐이다(`pull_request` 같은
    남의 코드 방아쇠는 시크릿을 쥐여 준다). 테스트가 이 전부를 글자로 묶고, 위반 12가지를 넣어 12가지 다 잡히는 것을
    확인했다. **GitHub 쪽에서 쓰기를 원천 차단하는 길은 스냅샷 저장소 관리자의 읽기 전용 배포 키뿐이다** — 그때는 이
    단계를 SSH 로 바꾼다.
    - **테스트는 단계를 읽으므로 워크플로와 잡에는 단계 밖에서 도는 것이 없어야 한다** (2026-10-02 검토). 첫 판 테스트는
      단계만 보고 시크릿을 `secrets.` 글자로만 세서, 재사용 워크플로를 부르며 `secrets: inherit` 를 단 잡 — 스냅샷 토큰을
      테스트가 안 읽는 코드에 넘긴다 — 이 초록으로 지나갔다. 지금은 워크플로 · 잡의 열쇠를 지금 모양으로 묶고(`uses` ·
      `secrets` · `container` · `services` · `env` · `defaults` 없음), 토큰 단계는 `name` · `env`(토큰 하나) · `run` 뿐이고
      (`shell` 과 env 의 `BASH_ENV` · `BASH_FUNC_*%%` 는 스크립트 첫 줄보다 먼저 돈다 — 로컬 bash 로 실측), 시크릿 표현식은
      읽어 들인 값 전체에서 대소문자 없이, 끝은 GitHub 처럼 따옴표 밖의 `}}` 로 센다(GitHub 는 `SECRETS.…` 도 받고 `run`
      안 셸 주석 줄의 `${{ }}` 도 푼다). 옛 테스트를 초록으로 지나던 위반 17가지를 넣어 17가지 다 잡힌다. 같은 날 셋을
      더 막았다: 토큰을 만지기 전에 PATH 를 `/usr/bin:/bin` 으로(앞 단계가 `GITHUB_PATH` 로 끼운 가짜 `base64` · `env`) ·
      `snapshot/` 이 이미 있으면 멈춤(심어 둔 `.git` 설정) · git 의 `-c` 는 토큰 머리글 하나, 받는 곳은 `origin` 하나
      (`url.*.insteadOf` · `http.proxy` · 주소 직접 적기로 토큰이 실린 요청을 딴 데로 못 돌린다). 위반 6가지 다 잡힌다.
    - 2026-10-01 첫 판은 `sudo unshare -n -- sudo -u runner` 였고 「코드 검토가 아니라 커널이 지킨다」고 적었는데 거짓이었다:
      러너 사용자는 비밀번호 없는 sudo 와 docker 그룹을 쥐어 이름공간을 나갈 수 있었고, 그 앞 단계가 공개 main 의
      `go test` 를 **네트워크를 쥔 채 스냅샷 옆에서** 돌렸고, 미는 단계는 가공기가 쓴 `out/` 을 그대로 git 저장소로 썼다
      (`.git` · 훅을 심으면 네트워크와 토큰이 있는 단계에서 돈다 — 재현됨).
  - **미는 단계는 가공기가 쓴 폴더를 믿지 않는다** — 원본(`snapshot/`)을 먼저 지우고, 정해 둔 이름의 보통 파일만 새
    폴더로 옮겨 그것만 민다(그 밖의 것이 있으면 멈춘다). git 은 전역·시스템 설정도 훅도 안 읽는다.
  - **`data` 브랜치는 그날 결과 커밋 하나(부모 없음)이고 강제로 민다.** 지난 데이터가 이력으로 쌓이지 않고 크기도
    안 자란다. `main` 은 워크플로만 든다 — 결과를 `main` 에 올리면 매일 워크플로와 데이터가 한 이력에 섞인다.
  - **가공 레포에는 가공기 코드가 없다 — 운영자가 고른 커밋(가공 레포의 Actions 변수 `EXPORTER_COMMIT`, 40자 sha)의
    `agent/` 를 받아 빌드한다.** 재료의 모양(`agent/facts.go`)과 합치기(`usageMerge.ts`)가 같은 커밋에서 같이 움직여야
    해서 코드는 이 저장소에 한 벌이다. **`main` 에 넣는 것만으로는 가공에 안 나간다** — 이 저장소는 공개라 `main` 에
    커밋 하나가 들어가는 것(계정 탈취 · 잘못된 병합)만으로 그 코드가 다음 날 아침 스냅샷 옆에서 돌면 안 된다. CI 가 초록인
    커밋을 읽어 본 사람이 변수를 그 sha 로 올려야 돈다(비었거나 sha 가 아니면 첫 단계에서 멈춘다 — 비운 ref 를 checkout 은
    기본 브랜치로 읽는다). 그 잡은 시크릿과 스냅샷을 쥐므로 **저장소 코드를 실행하는 `go test` · `go vet` 을 안 돌리고**
    빌드(`go build` 는 코드를 실행하지 않는다, cgo 끔)는 스냅샷을 받기 **전에** 끝낸다 — 테스트는 CI 의 `exporter` 잡에서만
    돈다. DuckDB 는 `snapshot.go` 의 `duckdbVersion` 을 받아 `agent/duckdb-linux-amd64.sha256` 과 맞을 때만 쓴다 —
    버전만 올리고 체크섬을 안 고치면 거기서 멈춘다(그게 맞다).
  - **재료의 모양을 바꾸면 형식 번호를 같이 올린다**(`agent/export.go` 의 `dataFormat` · `lib/usageData.ts` 의 `FORMAT`).
    화면은 `main` 에 들어가면 곧 Render 에 배포되고 재료는 `EXPORTER_COMMIT` 을 올려 다시 가공해야 바뀌어서 그 사이가 실제로
    생긴다 — 번호가 다르면 화면은 숫자 대신 「가공 데이터 형식(N)이 이 화면(M)과 다릅니다」를 띄운다(안 올리면 빈 칸 · NaN 이
    「기록 없음」처럼 조용히 선다). Render 배포가 끝나면 변수를 그 커밋으로 올리고 Run workflow.
- **가공 결과**: `manifest.json`(스냅샷 시각 · 가공 시각 · 커밋 · 가공기 버전) · `summary.json`(목록의 두 열과 판정
  재료) · `evidence.json`(자동 대조 근거) · `sales.json`(영업 인사이트) · `metrics.json`(「데이터 분석」의 전역 지표) ·
  `facts/index.json` → `facts/<묶음>.json`(상세의 크레딧 · 작업 성능 · 영상 분석 재료, 스페이스 하나씩). 묶음은
  엔터프라이즈마다 하나(`e1` …)와 나머지를 `space_seq % 16` 으로 나눈 `p00`~`p15` 라 계약 하나가 대개 파일 하나다.
  2026-09-14 스냅샷으로 스페이스 2,094 · 묶음 135 · 합계 약 10MB · 가장 큰 묶음 0.6MB.
- **가공 범위는 엔터프라이즈에 묶인 스페이스 ∪ 무료가 아닌 플랜을 구독한 스페이스 ∪ 엔터프라이즈 크레딧을 쓴 적이
  있는 스페이스다**(`agent/export.go` 의 `universeSQL`, 09-14 실측 990 + 1,101 + 3). 셋째는 계약이 끝나 플랜이 무료로
  돌아간 B2B 스페이스다 — 첫 판에는 없어서 그 계약의 화면이 「가공 범위에 없음」으로, 지급 회차 자동 대조가 멈췄다.
  밖의 번호는 목록에 「스냅샷에 없음」, 상세에 「가공 범위(엔터프라이즈·유료 스페이스)에 없습니다」로 서고, 계약의
  번호 **일부만** 밖이면 목록과 상세 머리에 「일부 스냅샷에 없음」을 그 번호와 함께 단다(`usageFor` 의 `missing` —
