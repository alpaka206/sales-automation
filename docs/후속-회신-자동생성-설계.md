# New 이후의 회신도 초안을 만든다 — 설계

> **읽는 이에게.** 자동 초안은 New 티켓에만 생기고, 그 뒤의 회신은 전부 빈 편집기였습니다.
> 이 문서는 「메일 발송」을 누르면 초안이 만들어지게 하는 계획입니다.
>
> 핵심은 **새 기계를 거의 안 만든다**는 것입니다 — 「초안 다시 쓰기」가 이미 New 관문을
> 일부러 비켜 가는 길을 갖고 있어서, 후속 초안은 그 길을 그대로 탑니다. 진짜 일은
> 3장입니다: **그 초안이 무엇에 답하는가.**
>
> 작성: 2026-09-07 · 운영자 지시

---

## 1. 한 줄 요약

「메일 발송」이 빈 초안 대신 **쓰인 초안**을 만든다. 무엇에 답할지는 두 갈래다 —
마지막 회신 뒤에 고객 메시지가 있으면 **그것에 답하고**, 없으면 같은 문의를 **더 자세히**
쓴다. 참고 문서는 「후속에만」 붙는 깊은 문서를 따로 둘 수 있게 한다.

```
                       첫 회신(New)        후속 회신
무엇에 답하나          최초 문의            새 고객 메시지 → 없으면 지난 문의를 더 자세히
참고 문서              scope: all|first     scope: all|followup
금액                   금지                  가능
언어                   문의 언어 + 한국어 대역 (둘 다 같음)
승인                   사람                  사람 (자동 발송 없음)
```

## 2. 지금 있는 것 — 새로 만들 필요가 없는 부분

| 필요한 것 | 이미 있는 것 | 자리 |
|---|---|---|
| New 가 아닌 티켓에 초안 쓰기 | 재생성 작업이 단계 관문을 비켜 간다 | `inbound.py:185` (`_draft_message_id`) |
| 기존 메시지에 덮어쓰기 | `_persist_placeholder(resume_message_id=…)` | `inbound.py` |
| 백그라운드 실행 · 재시도 · 리스 | `inbound_jobs` 워커 | `inbound_worker.py` |
| 화면의 「쓰는 중」 상태 | `status='drafting'` | 재생성이 쓰는 그 상태 |
| 문의 언어로 작성 | `reply.ensure_language` | `_draft_reply` CODE GUARD 1 |
| 한국어 대역 | `reply.korean_reading` → `messages.body_ko` | `_draft_reply` CODE GUARD 4 |
| 사람 승인 없이는 안 나감 | `_finalize_draft` 가 언제나 `pending_approval` | 불변식 |

그래서 4장(버튼)은 **가장 작은 조각**이고, 1~3장이 실제 작업이다.

## 3. 무엇에 답하는가 — 여기가 진짜 일이다

지금 코드를 그대로 후속에 태우면 **최초 문의에 다시 답한다.** 두 자리가 New 를 전제로
쓰여 있다.

### 3.1 고객의 마지막 말을 안 읽는다

`contact_info["last_message"]` 는 허브스팟이 준 **티켓 본문** = 최초 문의다. 후속 회신은
고객이 그 뒤에 보낸 말에 답해야 한다.

### 3.2 대화 맥락이 빈다

`_build_conversation_context` 는 `messages` 만 읽는다. 그런데 New 이후의 실제 대화는
`customer_interactions` 에 있다 — 허브스팟 스레드 수집기가 넣는 자리다(`ticket_history`).
`messages` 에는 우리가 이 콘솔에서 보낸 것만 있고, 허브스팟 화면에서 사람이 답한 것과
고객 답장은 **한 줄도 없다.**

### 3.3 「첫 회신인가」도 같은 이유로 틀린다

`_is_first_reply` 는 `Message.status == 'sent'` 만 센다. 허브스팟 화면에서 보낸 회신은
`messages` 에 없으므로, 실제로는 답을 보낸 티켓이 「첫 회신」으로 판정되고 **금액 금지
가드가 걸린다.**

### 3.4 그래서 이렇게 고친다

읽는 자리를 한 곳으로 모은다 — `messages` + `customer_interactions` 를 시간순으로 합친
하나의 대화. 세 함수가 그 위에 선다.

```python
_thread_events(conv_id)        # 두 표를 합친 시간순 목록 (direction 정규화 포함)
_latest_customer_message(...)  # 마지막 우리 회신 이후의 고객 메시지 (없으면 None)
_last_sent_reply(...)          # 마지막으로 나간 우리 회신 (본문 포함)
```

- `_build_conversation_context` 가 `_thread_events` 를 쓴다.
- `_is_first_reply` 는 「나간 회신이 하나라도 있나」를 `_thread_events` 로 판단한다.
- 후속 모드는 `_latest_customer_message` 의 유무로 갈린다.

**이 장은 「재생성」 버튼에도 그대로 이득이다** — 지금은 재생성도 같은 눈으로 대화를 본다.

## 4. 두 갈래 — 운영자 지시

### 4.1 `answer_new` — 마지막 회신 뒤에 고객 메시지가 있다

- `last_message` = 그 메시지
- 프롬프트: 「이 메시지에 답하라. 지난 회신은 맥락이다」
- 문서 라우터의 `inquiry` 도 그 메시지

### 4.2 `elaborate` — 답이 안 왔는데 한 번 더 쓴다

- `last_message` = 지난 고객 메시지(=원 문의)
- 프롬프트: 「이미 회신을 보냈다. **같은 문의를 더 자세히** 쓴다. 지난 회신에 이미 적은
  말을 되풀이하지 않는다. 지난 회신 본문은 아래와 같다」 + `_last_sent_reply` 의 본문
- 여기가 「후속에만」 문서가 실제로 쓰이는 자리다 — 처음에는 간단히 답하고, 더 물어오면
  깊은 문서를 붙여 자세히 쓴다.

### 4.3 어떻게 넣나

`pricing_rule` 과 **같은 방식**이다 — 프롬프트 변수 하나를 코드가 갈아 끼운다.

```
draft_reply.md 에 {{followup_rule}} 한 줄 추가
_FOLLOWUP_RULE_ANSWER / _FOLLOWUP_RULE_ELABORATE / "" (첫 회신)
```

프롬프트 파일을 새로 만들지 않는다. 회신의 형식·톤 규칙은 한 벌이어야 하고(CLAUDE.md),
파일이 둘이면 그 규칙이 두 곳에서 갈린다. 이 문장들은 형식 규칙이 아니라 `pricing_rule`
과 같은 종류의 **코드 가드 문장**이라 코드에 둔다.

## 5. 정책 문서 — `mode` 는 그대로 두고 `scope` 한 칸

### 5.1 왜 `mode` 를 늘리지 않나

지금 읽는 자리가 `mode == 'knowledge'` 다. `mode` 를 3~4값으로 늘리면 한 곳이라도 안
고쳤을 때 **그 문서가 라우터에서 조용히 사라진다.** `scope` 를 따로 두고 기본을 「모두」로
하면, 빠뜨린 자리는 많이 보여 줄 뿐 덜 보여 주지 않는다.

### 5.2 값

```
policy_sources.scope   all(기본) | first | followup     ← mode='knowledge' 일 때만 뜻이 있다
```

| 콘솔 표시 | mode | scope | 누가 읽나 |
|---|---|---|---|
| 항상 적용 | `rules` | — | 모든 프롬프트에 통째로 |
| 문의별 참고 · 모두 | `knowledge` | `all` | 첫 회신 + 후속 |
| 문의별 참고 · 후속에만 | `knowledge` | `followup` | 후속만 |
| 문의별 참고 · 첫 회신에만 | `knowledge` | `first` | 첫 회신만 |

운영자가 말한 「new 참고 / 모두 참고」는 설명을 따라가면 **같은 것**이다 — 후속도 New
문서를 읽는다고 했으므로 그것이 `all` 이다. 그래서 실제로 새로 생기는 것은 「후속에만」
하나고, 「첫 회신에만」은 값 하나 더 두는 값이다(회신 서식처럼 첫 메일에만 붙어야 하는
문서).

### 5.3 라벨의 출처는 한 곳

`MODES` 옆에 `SCOPES` 튜플을 둔다. 콘솔 폼과 목록이 같은 튜플을 읽는다 — 지금 `MODES` 가
그렇게 되어 있다(`policy_docs.MODES` 를 `ui_api` 가 import).

운영 문서 8편은 전부 `all` 로 들어간다. **오늘 동작이 안 바뀐다.**

## 6. 「메일 발송」 버튼

```
클릭
 → POST /tickets/{id}/reply : 지금처럼 행을 만들되 status='drafting'
 → enqueue_draft(message_id) : 같은 작업 큐에 draft_message_id 로 올림
 → 워커 → InboundAgent.handle → _draft_reply → _finalize_draft → pending_approval
```

- `request_redraft` 는 `send_failed|draft_failed` 만 받는다. 큐에 올리는 부분만
  `enqueue_draft(message_id, source)` 로 떼어 둘이 같이 쓴다 — **상태 관문은 재생성 쪽에
  그대로 남긴다**(안 그러면 재생성 버튼이 작성 중인 초안에도 걸린다).
- 화면은 손댈 것이 거의 없다. 이미 `drafting` 을 그릴 줄 알고, 다 되면 SSE 가 갱신한다.
- **동기 생성은 안 한다.** pro 티어 4000 토큰이라 버튼이 20~30초 멈추고 Render 프록시가
  끊을 수 있다.
- 빈 초안이 필요하면 편집기에서 지우면 된다. 버튼을 둘로 늘리지 않는다.

## 7. 순서와 되돌리기

| # | 무엇 | 배포 후 보이는 변화 | 되돌리기 |
|---|---|---|---|
| 1 | `scope` 열 · 콘솔 고르개 · `router_docs(stage)` | 없음 (전부 `all`) | 열만 두면 무해 |
| 2 | 대화 맥락이 접점 기록까지 읽는다 | 재생성 초안이 좋아진다 | 함수 되돌리기 |
| 3 | 후속 두 갈래 (`followup_rule`) | 없음 (아직 부르는 곳 없음) | 변수 빈 문자열 |
| 4 | 「메일 발송」이 초안을 만든다 | **버튼 동작이 바뀐다** | 이 커밋만 되돌리면 예전처럼 빈 초안 |

**2 → 3 → 4 순서는 바꿀 수 없다.** 2 없이 4를 켜면 후속 초안이 최초 문의에 다시 답한다.
1 은 독립이라 언제 해도 된다.

---

## 8. 안전 — 바뀌지 않는 것

- **자동 발송은 없다.** 후속 초안도 `pending_approval` 로 서고 사람이 승인한다. 이 계획은
  `_finalize_draft` 를 건드리지 않는다.
- **New 관문은 그대로다.** 저절로 생기는 초안은 지금도 New 뿐이다. 여기서 여는 길은
  **운영자가 버튼을 누른 것**뿐이고, 그건 재생성이 이미 지나던 길이다.
- 발송 관문(언어·수신자·safe mode)은 손대지 않는다. 후속 초안이 자동 초안과 **같은 행**을
  쓰므로 승인·번역·발송 라우트가 그대로 걸린다.
- `LIVE_EXTERNAL_WRITES` 와 무관하다 — 이 계획에 외부 쓰기가 없다.

## 10. 검사

- 문서: 기본값 `all` 이면 오늘과 같은 후보가 나온다 / `followup` 문서는 첫 회신 후보에
  없다 / `first` 문서는 후속 후보에 없다
- 맥락: 접점 기록만 있는 티켓에서 대화 맥락이 비지 않는다 / 허브스팟에서 보낸 회신이
  있으면 「첫 회신」이 아니다(금액 가드가 안 걸린다)
- 갈래: 마지막 회신 뒤 고객 메시지가 있으면 `answer_new`, 없으면 `elaborate` — 그리고
  `elaborate` 프롬프트에 지난 회신 본문이 실린다
- 버튼: `drafting` 을 만들고 큐에 올린다 / 티켓 없는 문의는 400 그대로 / 열려 있는 초안이
  있으면 새로 만들지 않고 그것을 연다(지금 규칙 유지)
